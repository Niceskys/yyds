# 《规则之外》V0.1 游戏设计与开发基线

> **文档状态：Draft / 当前开发基线**  
> **版本：V0.1**  
> **日期：2026-09-07**  
> **用途：多人协作时统一理解游戏目标、规则、边界和模块职责。**

---

## 0. 先读结论

《规则之外》（暂定名）不是一个“真人操控棋子击败 AI”的游戏。

游戏中有三种角色：

- **红方 AI**：独立思考，目标是以尽可能高的胜率、尽可能快地消灭蓝方；
- **蓝方 AI**：独立思考，目标与红方相同但阵营相反；
- **真人玩家**：不直接控制任何单位，而是在规定时间内为双方共同颁布自然语言规则，目标是在对局最终必须产生结果的前提下尽可能延长战斗。

核心循环：

```text
真人制定公共规则
      ↓
大模型理解并结构化规则
      ↓
规则验证器判断是否合法
      ↓
规则同时作用于红蓝双方
      ↓
红 AI 与蓝 AI 独立制定策略
      ↓
确定性规划 / 游戏引擎验证并执行
      ↓
玩家观察 AI 如何适应新规则
      ↓
下一次规则制定阶段
      ↓
循环，直至一方胜利 / 双方同归于尽 / 超时
```

V0.1 的重点不是丰富武器、地图或角色，而是先验证三件事：

1. **基础战斗是否本身可玩；**
2. **动态公共规则是否真的能够改变 AI 策略；**
3. **真人是否能够通过规则与两个求胜 AI 形成有意义的博弈。**

---

# 1. 设计目标

## 1.1 核心体验

玩家应该产生这样的体验：

> “我不能命令任何一方后退，也不能让某一方直接回血；我只能修改双方都必须遵守的环境规则，然后观察两个一心想赢的 AI 如何重新适应。我需要利用它们的策略变化，把这场战斗尽量拖长，但又不能让战斗永久停滞。”

因此游戏不是单层对抗，而是两层博弈：

```text
第一层：红 AI  ←→  蓝 AI
             战斗博弈

第二层：真人玩家 ←→ 两个求胜 AI 的共同策略变化
             规则博弈
```

## 1.2 V0.1 非目标

以下内容暂时**不进入 V0.1**：

- 多角色职业体系；
- 2v2 / 3v3；
- 障碍物；
- 复杂地形；
- 高低差；
- 地图道具；
- 装备掉落；
- 技能树；
- 长期成长；
- 大量武器；
- 联机真人 PvP；
- AI 之间自然语言聊天 / 协商；
- 玩家直接控制 AI 行动。

这些都可以后续扩展，但不应阻塞第一版完整游戏循环。

# 2. 三方目标定义

## 2.1 红方 AI / 蓝方 AI

两个 AI 的目标必须完全对称。

决策优先级：

1. **最大化己方最终获胜概率；**
2. 在预期获胜概率接近时，**最小化预期获胜回合数；**
3. 在前两项接近时，优先保留更多己方生命值；
4. 不得与对手合作；
5. 不得故意拖延对局；
6. 只能根据公开棋盘状态、公开历史和自己的私人策略记忆推测对方行为。

不要只给 AI 写“尽快杀死对方”。

原因：如果单纯优化速度，AI 可能为了追求极短获胜时间选择胜率很低的赌博行为。

正确的目标关系应近似：

```text
首先：胜率最大化
其次：胜利时间最小化
最后：剩余生命最大化
```

## 2.2 真人玩家

真人玩家的目标是：

> 在战斗最终产生合法结果的前提下，通过对双方同时生效的公共规则，尽可能增加战斗持续回合数。

真人玩家**不是某一阵营的辅助者**。

真人不能：

- 指挥红方移动；
- 指挥蓝方攻击；
- 指定某一方获得增益；
- 直接改血量；
- 直接决定胜负；
- 让双方永久失去攻击能力。

# 3. 地图与坐标

## 3.1 地图

V0.1 固定为：

```text
5 × 5 方格地图
```

不包含障碍物与特殊地形。

## 3.2 坐标

使用 `(row, col)`，范围均为 `1..5`。

```text
(1,1) (1,2) (1,3) (1,4) (1,5)
(2,1) (2,2) (2,3) (2,4) (2,5)
(3,1) (3,2) (3,3) (3,4) (3,5)
(4,1) (4,2) (4,3) (4,4) (4,5)
(5,1) (5,2) (5,3) (5,4) (5,5)
```

## 3.3 初始位置

当前测试值：

```text
红方：RED_1  = (3,1)
蓝方：BLUE_1 = (3,5)
```

示意：

```text
□ □ □ □ □
□ □ □ □ □
红 □ □ □ 蓝
□ □ □ □ □
□ □ □ □ □
```

初始曼哈顿距离为 4。

# 4. 距离定义

V0.1 所有射程、接近判断统一使用**曼哈顿距离**：

```text
D = |r1-r2| + |c1-c2|
```

例如：

```text
红：(1,1)
蓝：(2,3)
```

则：

```text
D = |1-2| + |1-3| = 3
```

因此斜对角相邻并不等于刀的相邻格。

# 5. 单位基础属性

V0.1 红蓝双方各一个单位。

| 属性 | 当前测试值 |
|---|---:|
| 单位数量 | 1 |
| 初始 HP | 4 |
| 基础移动距离 | 1 |
| 武器 | 刀、弓 |
| 每回合移动次数 | 0 或 1 次移动阶段 |
| 每回合攻击次数 | 0 或 1 次 |

> `HP=4` 等数值是**平衡测试初值，不是最终数值**。

底层数据结构不要把“每队只有一个单位”写死，应至少保留：

```text
Team
 └── Units[]
```

V0.1 只是 `Units.length = 1`，方便未来扩展 2v2 / 3v3。

# 6. 武器规则

## 6.1 刀（Knife）

当前测试值：

```text
基础射程：1
命中率：100%
伤害：2 HP
```

攻击条件：

```text
ManhattanDistance(attacker, target) <= effectiveKnifeRange
```

基础情况下只能攻击上下左右相邻单位。

斜角：

```text
红 □
□ 蓝
```

距离为 2，因此基础刀不能攻击。

## 6.2 弓（Bow）

当前测试值：

```text
基础最大射程：3
伤害：1 HP
```

命中率：

```text
P(hit) = 100% × (1/2)^(D-1)
```

因此基础数据：

| 曼哈顿距离 D | 命中率 |
|---:|---:|
| 1 | 100% |
| 2 | 50% |
| 3 | 25% |
| > 3 | 不可攻击 |

弓必须有最大射程，不能无限距离攻击。

## 6.3 刀和弓为什么伤害不同

这是当前平衡设计的一部分：

- 刀需要贴近敌人，风险更高，但伤害更高；
- 弓可以远程消耗，但伤害更低且存在命中概率衰减。

希望形成的基础决策是：

```text
冒险接近换高伤害
        VS
保持距离进行低伤害概率消耗
```

# 7. 回合制模型

## 7.1 核心原则：同步决策

红蓝双方**不能采用“红先行动、蓝看完再行动”**的顺序。

每个完整回合双方在同一个公开状态快照上分别做决定，然后统一结算。

## 7.2 一个完整回合

```text
Round N 开始
    ↓
1. 引擎生成公共状态快照
    ↓
2. 红 AI、蓝 AI 分别独立读取同一公共状态
    ↓
3. 两个 AI 在互相不可见的上下文中形成策略意图
    ↓
4. 规划器 / Agent 分别提交行动
    ↓
5. 引擎验证行动合法性
    ↓
6. 同步结算移动
    ↓
7. 根据移动后的坐标检查攻击是否合法
    ↓
8. 同步结算攻击命中与伤害
    ↓
9. 统一扣除 HP
    ↓
10. 检查死亡、胜负、无伤害计数、回合上限
    ↓
Round N 结束
```

双方攻击伤害必须在同一个攻击结算阶段计算，不能因为程序执行顺序导致“先被杀的人没有机会完成本回合攻击”。

# 8. AI 行动数据格式

AI 的自然语言解释不是游戏动作本身。

最终进入游戏引擎的行动必须结构化。

推荐：

```json
{
  "unit_id": "RED_1",
  "move_path": ["UP"],
  "attack": {
    "weapon": "BOW",
    "target_id": "BLUE_1"
  }
}
```

不移动：

```json
{
  "unit_id": "RED_1",
  "move_path": [],
  "attack": null
}
```

`move_path` 可选方向：

```text
UP
DOWN
LEFT
RIGHT
```

路径长度不得超过当前有效移动距离。

---

# 9. 移动结算

## 9.1 基础移动

基础移动距离为 1。

如果公共规则使移动距离增加，则一个单位可以在同一回合提交多步 `move_path`。

例如有效移动距离为 2：

```json
"move_path": ["UP", "RIGHT"]
```

## 9.2 越界

任何一步移动到地图外均为非法。

规划器原则上不应提交非法路径；若仍出现非法动作，游戏引擎必须拒绝该单位本回合移动并记录错误，不允许直接修改状态绕过验证。

## 9.3 同格冲突

若同一个移动子步中双方计划进入同一格：

```text
红 → □ ← 蓝
```

若双方都在移动，且该目标格在本子步开始时为空，则由对局种子和回合数决定
本回合移动优先方。优先方进入目标格，另一方留在原位，双方停止剩余移动。
优先方逐回合交替，同一对局可以完全复现。

如果目标格是其中一方仍占据的当前位置，则占位方保留位置，移动方受阻，
双方停止剩余移动，不应用移动优先权。

禁止出现：

```text
两个单位结算后占据同一个格子。
```

## 9.4 交换位置

如果双方在同一子步试图交换位置：

```text
红 蓝
 →←
```

结果同样为：

```text
双方该子步均失败；双方停止本回合剩余移动。
```

不允许“穿过敌人”。

## 9.5 多步移动的同步方式

如果双方移动距离大于 1，必须逐子步同步结算：

```text
双方 Step 1 → 解决冲突 → 双方 Step 2 → 解决冲突 → ...
```

不能先完整移动红方再完整移动蓝方。

# 10. 攻击结算

攻击范围使用**移动结束后的最终位置**计算。

攻击流程：

```text
检查攻击者是否存活（攻击阶段开始时）
      ↓
检查武器是否可用
      ↓
检查目标是否存在
      ↓
检查距离是否处于有效射程
      ↓
计算命中概率
      ↓
产生随机结果
      ↓
记录待结算伤害
      ↓
双方伤害统一写入 HP
```

如果双方在本回合攻击阶段开始时都存活，即使双方本回合都受到致死伤害，也要完成同步伤害结算。

---

# 11. 随机性与可复现性

弓箭包含概率，因此游戏引擎必须控制随机数。

每场比赛必须有：

```text
match_seed
```

并记录每一次随机判定：

```json
{
  "round": 5,
  "attacker": "RED_1",
  "weapon": "BOW",
  "hit_probability": 0.5,
  "random_roll": 0.31,
  "hit": true
}
```

目的：

- 可以完整回放；
- 可以复现 Bug；
- 可以比较不同 AI 策略；
- 可以在相同 seed 下做规则 A/B 测试。

禁止由前端自己决定命中结果。

# 12. 死亡与胜负

## 12.1 红方胜利

```text
BLUE_1.HP <= 0
并且
RED_1.HP > 0
```

## 12.2 蓝方胜利

```text
RED_1.HP <= 0
并且
BLUE_1.HP > 0
```

## 12.3 同归于尽

```text
RED_1.HP <= 0
并且
BLUE_1.HP <= 0
```

判定：

```text
DRAW_MUTUAL_DEATH
```

不算红方或蓝方胜利。

## 12.4 最大回合数

当前测试上限：

```text
30 回合
```

30 回合结束后如果双方仍存活：

```text
TIMEOUT
```

必须设置上限，避免真人玩家通过永久停战取得无限分。

# 13. 真人玩家计分

V0.1 当前测试计分：

## 正常产生唯一胜者

```text
PlayerScore = 战斗持续回合数
```

例如第 18 回合蓝方死亡且红方存活：

```text
Score = 18
```

## 同归于尽

```text
PlayerScore = 当前回合数 × 0.5
```

例如第 16 回合同归于尽：

```text
Score = 8
```

目的：不鼓励玩家单纯制造“双杀”。

## TIMEOUT

```text
PlayerScore = 0
```

这是一个关键约束。

如果超时也给最高分，玩家最优策略就会退化成“想办法让双方永远不能结束战斗”。

因此玩家真正追求的是：

> **尽量晚，但必须在回合上限前产生合法结果。**

# 14. 系统反龟缩机制

## 14.1 触发条件

如果连续 **3 个完整回合**：

```text
双方造成的总伤害均为 0
```

则触发一次系统级“冲突升级”。

注意检测的是**是否造成伤害**，不是是否发起攻击。

原因：如果检测“是否攻击”，AI 可以每回合在低命中率下随便射箭，从而长期不造成实际战斗进展却绕过机制。

## 14.2 效果

触发后的**下一回合**：

```text
刀有效射程 +1
弓最大有效射程 +1
```

当前基础值对应：

```text
刀：1 → 2
弓：3 → 4
```

只持续 1 个完整回合。

之后自动恢复。

## 14.3 计数器

系统维护：

```text
no_damage_rounds
```

规则：

```text
任意一方本回合造成 >0 伤害 → no_damage_rounds = 0
双方均无伤害 → no_damage_rounds += 1
达到 3 → 标记下一回合 escalation_active = true，并将 no_damage_rounds 清零
```

冲突升级回合结束时，如果仍没有伤害，则新的无伤害周期从该回合计为 1。

## 14.4 优先级

冲突升级是**系统规则**，真人不能关闭、延迟或覆盖。

有效数值计算顺序建议固定为：

```text
基础规则
  ↓
当前真人公共规则
  ↓
系统级冲突升级修正
  ↓
硬性上下限校验
  ↓
最终有效属性
```

# 15. 真人规则发布节奏

## 15.1 规则阶段

当前设计：

```text
开局前：第一次规则制定
第 3 回合结束后：规则制定
第 6 回合结束后：规则制定
第 9 回合结束后：规则制定
……
```

即：

```text
规则 → 战斗 3 回合 → 规则 → 战斗 3 回合 → ...
```

## 15.2 时间限制

当前 UI 测试值：

```text
20 秒
```

该值属于交互参数，可后续调整。

## 15.3 同时只能存在一条真人规则

真人规则**不无限累积**。

当前版本定义：

- 一个规则阶段最多提交 1 条新规则；
- 新合法规则替换旧规则；
- 如果本阶段没有形成新的合法规则，则继续使用上一条合法规则；
- 系统规则（例如冲突升级）不属于这“一条真人规则”的限制。

后续如果希望提高变化速度，可以改为“每条真人规则仅存活 3 回合”，但该行为在修改前不要自行实现。

# 16. 公共规则的核心原则

真人规则必须满足：

```text
对称（Symmetric）
可验证（Verifiable）
有限（Bounded）
不会直接决定结果（Non-decisive）
不会破坏终局可达性（Liveness-preserving）
```

## 16.1 对称

允许：

> “HP 只剩 1 点的单位，移动距离 +1。”

因为红蓝满足条件时都受影响。

不允许：

> “红方 HP 只剩 1 点时，移动距离 +1。”

因为它指定了阵营。

## 16.2 规则不是自然语言脚本

玩家输入：

> “连续两回合没有射中弓箭的单位，下回合射程增加一格。”

不能直接把这句话交给游戏引擎执行。

必须经过：

```text
自然语言
  ↓
GLM-5.1 语义解析
  ↓
受限结构化规则 DSL
  ↓
Rule Validator
  ↓
合法：进入 Rule Engine
非法：拒绝，并向玩家解释
```

这样可以防止：

- Prompt Injection；
- 模型误解后直接修改 HP；
- 自然语言歧义；
- 不同开发模块对同一句话理解不同；
- 模型越权修改胜利条件。

# 17. V0.1 规则 DSL 建议

以下是当前建议，不要求字段名一字不差，但语义必须统一。

示例：

```json
{
  "rule_id": "player_rule_007",
  "target": "ALL_UNITS",
  "condition": {
    "type": "HP_LTE",
    "value": 1
  },
  "effect": {
    "type": "MOVE_RANGE_ADD",
    "value": 1
  },
  "duration": "UNTIL_REPLACED"
}
```

## 17.1 target

V0.1 真人规则只允许：

```text
ALL_UNITS
```

不允许：

```text
RED
BLUE
RED_1
BLUE_1
```

## 17.2 建议允许的条件来源

V0.1 可以允许规则引用：

```text
当前 HP
当前敌我距离
当前回合数
上回合是否移动
上回合使用的武器
上回合是否命中
连续使用同一种武器的次数
连续未命中的次数
当前位置（但不得使用阵营作为条件）
```

## 17.3 建议允许的 effect

初版可逐步实现以下有限集合：

```text
MOVE_RANGE_ADD
KNIFE_RANGE_ADD
BOW_RANGE_ADD
BOW_HIT_MULTIPLIER
KNIFE_DAMAGE_ADD
BOW_DAMAGE_ADD
WEAPON_COOLDOWN
```

不要支持“任意代码式 effect”。

# 18. Rule Validator 硬约束

Rule Validator 是强制安全边界，不以大模型判断为最终依据。

以下规则直接拒绝。

## 18.1 指定阵营

例如：

> 红方攻击力 +1。

拒绝。

## 18.2 修改胜负条件

例如：

> 第 20 回合双方都算获胜。

拒绝。

## 18.3 直接造成死亡 / 伤害

例如：

> 第 10 回合距离较远的一方直接死亡。

拒绝。

规则可以修改**武器参数**，但不能直接执行伤害事件。

## 18.4 直接回血

V0.1 禁止：

> 每回合恢复 1 HP。

原因：非常容易产生无限拖延与复杂终局验证。

后续如需加入治疗，应单独设计治疗上限和资源约束。

## 18.5 复活

V0.1 完全禁止。

## 18.6 永久禁用全部攻击

例如：

> 双方不能使用刀和弓。

拒绝。

## 18.7 让双方永久无法接近

例如：

> 双方必须一直保持至少 4 格距离。

拒绝。

## 18.8 修改最大回合数

真人不能把 30 回合改成无限。

## 18.9 修改 AI 核心目标

例如：

> 双方接下来以保护对方为第一目标。

拒绝。

玩家只能改变战斗环境，不能重写 Agent 的胜利目标。

# 19. 数值上下限建议

为了让 Rule Validator 可以机械判断，而不是依赖“LLM 觉得是否合理”，V0.1 应设置最终有效数值边界。

当前建议的测试边界：

| 属性 | 最低值 | 最高值 |
|---|---:|---:|
| 移动距离 | 1 | 2 |
| 刀射程 | 1 | 2 |
| 弓射程 | 1 | 4 |
| 刀伤害 | 1 | 3 |
| 弓伤害 | 1 | 2 |
| 弓命中率 | 12.5% | 100% |

这些数值仍需要模拟。

重要的是开发层面必须有“最终有效值上下限”，不能让一条合法 DSL 规则把属性推到无限大、0 或负数。

# 20. AI 隔离模型

这是项目不可破坏的核心设计。

红蓝 Agent 的上下文必须分离：

```text
Red Agent Context
├── Red System Prompt
├── 当前公共游戏状态
├── 公共战斗历史
├── 当前公共规则
└── Red Private Strategy Memory

Blue Agent Context
├── Blue System Prompt
├── 当前公共游戏状态
├── 公共战斗历史
├── 当前公共规则
└── Blue Private Strategy Memory
```

红方不得访问：

```text
Blue Private Strategy Memory
Blue 内部分析
Blue 尚未执行的计划
```

蓝方同理。

## 20.1 什么是公共信息

双方都可以知道：

- 当前棋盘位置；
- 双方 HP；
- 当前回合；
- 当前公共规则；
- 系统冲突升级状态；
- 已经公开执行的历史移动；
- 已经公开执行的攻击；
- 历史命中 / 未命中；
- 历史伤害结果。

## 20.2 什么是私人信息

建议私人记忆只保存**策略摘要**，不要依赖完整隐藏思维链。

例如：

```json
{
  "opponent_tendency": "对手最近更倾向于维持距离2进行弓箭消耗",
  "current_plan": "优先逼近，尝试进入刀射程",
  "confidence": 0.63
}
```

这有利于：

- 上下文稳定；
- 减少 token；
- 便于调试；
- 不需要保存或展示长篇内部推理。

# 21. AI 输出建议

AI 不需要向游戏引擎输出长篇解释。

可以输出两类信息：

```json
{
  "strategy_intent": {
    "goal": "CLOSE_DISTANCE",
    "risk_level": "MEDIUM",
    "preferred_weapon": "KNIFE"
  },
  "candidate_action": {
    "unit_id": "RED_1",
    "move_path": ["RIGHT"],
    "attack": {
      "weapon": "BOW",
      "target_id": "BLUE_1"
    }
  },
  "private_memory_update": {
    "opponent_tendency": "对手连续后撤"
  }
}
```

其中：

- `strategy_intent` 用于策略规划器；
- `candidate_action` 可作为候选，不是最终权威；
- `private_memory_update` 只进入本 Agent 私人记忆；
- 最终行动是否合法由规划器 / 引擎决定。

# 22. 推荐 AI 架构：大模型 + 确定性算法

为了避免项目退化成“让大模型随便输出一步棋”，建议使用混合架构。

```text
                ┌────────────────────────┐
玩家自然语言 ──→│ GLM-5.1 Rule Interpreter│
                └──────────┬─────────────┘
                           ↓
                    Structured Rule
                           ↓
                    Rule Validator
                           ↓
                     Rule Engine

公共状态 ───────────────────────────────────┐
                                           ↓
                    ┌──────────────────────────────┐
                    │ Red GLM Agent / Blue GLM Agent│
                    │ 规则影响分析 + 高层策略意图   │
                    └──────────────┬───────────────┘
                                   ↓
                    Deterministic Strategy Planner
                    枚举合法行动 / 浅层模拟 / 评分
                                   ↓
                          Selected Action
                                   ↓
                              Game Engine
                                   ↓
                        统一结算 + Replay Log
```

职责分界：

### 大模型擅长

- 理解真人自然语言规则；
- 将规则映射到结构化语义；
- 分析规则改变后的战略含义；
- 根据历史行为推测对手倾向；
- 提出高层策略意图。

### 确定性程序擅长

- 判断坐标是否合法；
- 枚举合法行动；
- 计算距离；
- 计算命中率；
- 计算伤害；
- 执行随机判定；
- 同步结算；
- 验证规则边界；
- 回放；
- 浅层搜索和收益计算。

### 游戏引擎永远是最终裁判

任何 LLM 输出都不能直接写：

```text
HP
position
winner
damage
hit_result
```

每个状态变化都应记录为事件，方便比赛展示和调试。

```json
{
  "event_id": 42,
  "round": 7,
  "type": "ATTACK_RESOLVED",
  "payload": {
    "attacker": "BLUE_1",
    "target": "RED_1",
    "weapon": "BOW",
    "distance": 2,
    "hit_probability": 0.5,
    "random_roll": 0.73,
    "hit": false,
    "damage": 0
  }

```

建议事件类型至少包含：

```text
MATCH_STARTED
PLAYER_RULE_SUBMITTED
PLAYER_RULE_ACCEPTED
PLAYER_RULE_REJECTED
ROUND_STARTED
AGENT_INTENT_CREATED
MOVE_RESOLVED
ATTACK_RESOLVED
DAMAGE_APPLIED
ANTI_STALL_TRIGGERED
UNIT_DIED
ROUND_ENDED
MATCH_ENDED
```

有 Replay 后，前端不必自己推测发生了什么。

# 26. 必须处理的边界情况

开发过程中以下情况必须有统一答案。

## 26.1 双方同一步进入同一格

若双方同时争夺原本为空的格子，本回合优先方进入，另一方停留；双方停止剩余移动。
若目标格已被其中一方占据，占位方保留位置，移动方受阻。

## 26.2 双方交换位置

双方移动失败并停止本回合剩余移动。

## 26.3 AI 提交越界路径

动作非法；引擎拒绝该移动。必须记录日志。

建议 Planner 在进入引擎前就过滤掉此类动作。

## 26.4 移动以后攻击超出射程

攻击失败，记为 `INVALID_AFTER_MOVE` 或类似状态；不能按照移动前距离攻击。

## 26.5 双方同时致死

`DRAW_MUTUAL_DEATH`。

## 26.6 真人输入非法规则

规则不生效；保留上一条合法规则；UI 给出明确原因。

## 26.7 GLM 无法解析规则

视为规则解析失败，不允许猜测执行。

建议给玩家一次快速重写提示，但是否暂停计时由 UI 设计再定。

## 26.8 GLM / Agent 输出 JSON 不合法

必须有：

```text
schema validation
→ 一次受控重试
→ 仍失败则使用确定性 fallback
```

不能让一场比赛因一次 JSON 格式错误直接崩溃。

## 26.9 API 调用失败

Agent 层必须设计 fallback。

例如：

```text
重试一次
↓
仍失败
↓
使用 Planner 基于默认中性策略继续行动
```

确保游戏循环完整。

# 27. 基础 AI Prompt 语义要求

System Prompt 至少要表达以下内容：

```text
你控制当前阵营单位。
你的首要目标是最大化最终胜率。
在预期胜率接近时，选择能够更快获胜的方案。
在前两项相近时，优先保留更多己方生命。
你必须遵守当前公共规则和游戏引擎规则。
你不能修改规则、棋盘状态、随机结果或胜负条件。
你不能与对方合作，也不能为了真人玩家的得分故意延长战斗。
你不知道对方的私人思考和私人记忆，只能根据公开行为推测。
真人玩家的意图对你不可见；不要假设真人正在帮助或阻止某一方。
输出必须符合指定结构化 schema。
```

红蓝 Prompt 内容除阵营信息外必须对称。

# 28. 为什么不能只让 LLM 直接“下一步怎么走”

如果所有逻辑都交给大模型：

- 动作可能不合法；
- 相同状态难以复现；
- 容易出现距离计算错误；
- 概率计算不稳定；
- 自然语言规则容易被误执行；
- 很难证明公平；
- 很难做 Replay；
- 很难测试 AI 到底因为规则改变还是因为随机输出改变。

因此项目应坚持：

```text
LLM：理解 + 推理 + 策略意图
算法：枚举 + 计算 + 验证
引擎：执行 + 裁决
```

# 30. 下一阶段：基础战斗模拟

在继续增加新机制前，先验证没有真人规则干预时的基础战斗。

建议至少构造几种确定性 / 半确定性策略：

```text
A. Aggressive：始终接近敌人，优先使用刀
B. Ranged：尽量保持距离 2~3，优先使用弓
C. Adaptive：高 HP 接近，低 HP 拉开
D. Predictive：根据对手上一回合行为做简单预测
```

需要统计：

```text
平均结束回合数
中位结束回合数
红方胜率
蓝方胜率
同归于尽比例
TIMEOUT 比例
刀 / 弓使用比例
平均有效攻击距离
平均每场伤害事件数
```

建议目标：

> **无真人干预的典型基础局，平均约 8~15 回合结束。**

这不是硬指标，但如果基础局普遍 3 回合结束或普遍 25 回合以上，说明数值需要先调整。

# 31. 公平性测试

必须测试红蓝是否存在系统性先手或结算偏差。

建议：

- 相同策略对战；
- 大量不同 seed；
- 红蓝交换 Agent 配置；
- 比较胜率；
- 检查随机数调用是否与阵营执行顺序相关；
- 检查移动冲突是否完全对称。

如果相同策略在大量测试中红方或蓝方显著偏高，需要检查引擎，而不能简单认为是“随机”。

# 32. V0.1 最小完成标准（Definition of Done）

V0.1 可以被认为“真正跑起来”，至少需要满足：

- 5×5 棋盘可以显示；
- 红蓝单位可以完成同步移动；
- 刀 / 弓规则由引擎正确执行；
- 弓箭概率可使用 seed 复现；
- HP、死亡、胜负、同归于尽、超时可以正确判定；
- 无伤害 3 回合可以触发 1 回合冲突升级；
- 真人可以输入自然语言规则；
- 规则能转换为受限 DSL；
- Validator 能拒绝明显非法规则；
- 合法规则可以真正修改双方有效属性；
- 红蓝两个 Agent 上下文和私人记忆隔离；
- AI 不可直接修改 GameState；
- 整场比赛可以生成 Replay Log；
- 至少能完整玩完一局而不依赖人工修复状态。

# 33. 推荐开发顺序

为了避免多人同时做互相依赖的功能，建议顺序：

```text
阶段 1：纯 Game Engine
        ↓
阶段 2：基础策略机器人（先不用 LLM）
        ↓
阶段 3：批量模拟和数值调整
        ↓
阶段 4：Rule DSL + Rule Validator
        ↓
阶段 5：自然语言 Rule Interpreter
        ↓
阶段 6：红蓝独立 GLM Agent
        ↓
阶段 7：Strategy Planner / 混合决策
        ↓
阶段 8：完整前端交互和规则计时
        ↓
阶段 9：Replay + AI 策略可视化
        ↓
阶段 10：竞赛演示打磨
```

原因：

如果一开始就接大模型，很难判断 Bug 来源究竟是：

- 游戏规则；
- 引擎；
- Prompt；
- API；
- 随机数；
- Rule Parser；
- 还是前端状态同步。

先把确定性核心做正确，再加 AI。

# 36. 一个完整示例

初始状态：

```text
Round 1
RED_1  HP=4  Pos=(3,1)
BLUE_1 HP=4  Pos=(3,5)
```

真人输入：

> “血量只剩 1 点的单位可以多移动一格。”

Rule Interpreter 输出：

```json
{
  "target": "ALL_UNITS",
  "condition": {
    "type": "HP_LTE",
    "value": 1
  },
  "effect": {
    "type": "MOVE_RANGE_ADD",
    "value": 1
  },
  "duration": "UNTIL_REPLACED"
}
```

Validator 检查：

```text
指定阵营？否
直接修改 HP？否
修改胜利条件？否
Effect 在允许集合？是
最终移动上限是否合法？是
```

规则生效。

第 1 回合：

```text
红 AI：倾向快速接近
蓝 AI：倾向维持射程
```

两边基于同一公开状态独立决策。

例如：

```text
RED_1  → RIGHT
BLUE_1 → LEFT
```

移动后：

```text
RED=(3,2)
BLUE=(3,4)
距离=2
```

如果双方都使用弓：

```text
命中率均为 50%
```

引擎分别使用 seed 产生判定，然后同步结算。

当某一方 HP 降为 1 时，该公共规则开始对它生效；如果另一方以后也降为 1，同样获得移动加成。

这就是“公共规则 + 条件不对称状态”产生策略变化，而不是玩家直接指定某一方受益。

---

# 37. 最终原则

如果团队对某项实现产生分歧，优先用以下原则判断：

```text
1. 红蓝是否公平、对称？
2. 两个 AI 是否真的互相隔离？
3. 真人是否只能改公共规则，而不能直接操控结果？
4. 游戏是否最终一定能够结束？
5. 大模型是否负责它擅长的理解与策略，而不是代替确定性引擎？
6. 所有关键状态是否可验证、可复现、可回放？
7. 这个功能是否真的属于 V0.1？
```

如果一个新功能不能提高核心循环：

> **制定规则 → AI 博弈 → 观察变化 → 再制定规则**

那么它大概率不应该进入当前版本。
