# 《规则之外》正式游玩流程 V0.2

状态：**当前产品玩法基线（Normative）**  
日期：2026-09-08  
适用范围：第一条真人可玩 MVP 纵向切片

> 本文取代旧文档中“Round 1 前先制定规则 / 每 3 回合进入一次规则阶段”的产品流程。
>
> V0.1 相关实验、Gate、历史文档仍保留作为证据，不应被改写成从未存在过。

---

## 1. 产品一句话

真人玩家不直接控制棋子，而是观察两个各自以获胜为目标的独立 AI，并在**每个完整回合结束后**决定是否替换一条同时约束红蓝双方的公共规则，目标是在不断升高的战斗压力下尽可能延长对局。

三个角色的目标不同：

| 角色 | 目标 |
|---|---|
| 红方 AI | 击败蓝方 |
| 蓝方 AI | 击败红方 |
| 真人玩家 | 尽量延长对局回合数 |

玩家不是红方，也不是蓝方。

---

# 2. 什么算一个回合

一个完整回合定义为：

```text
红方读取同一回合开始状态
蓝方读取同一回合开始状态
↓
红方 AI 独立产生公开策略
蓝方 AI 独立产生公开策略
↓
双方策略锁定
↓
确定性 Planner 分别生成合法具体动作
↓
Engine 同步移动 / 攻击 / 结算
↓
HP、位置、事件、胜负更新
↓
这一回合完成
```

红方行动一次、蓝方行动一次**合起来才是一个回合**。

AI/provider 的实际响应秒数不计入玩家成绩。

---

# 3. 开局流程

初始页面保持极简：

```text
《规则之外》

[开始游戏]
```

点击后：

```text
创建对局
↓
进入游玩界面
↓
第 1 回合自动开始
```

## 第 1 回合硬规则

第 1 回合开始前：

- 玩家**不能制定规则**；
- `active_rule = null`；
- 不存在 Phase 0；
- 玩家先观察一轮无玩家规则的基线战斗。

第 1 回合结算完成后，第一次进入玩家决策阶段。

---

# 4. 玩家决策阶段（每个非终局回合之后）

每个完整回合结算完成且比赛未结束时：

```text
游戏暂停
↓
玩家观察棋盘 / HP / 双方公开策略 / 实际行动 / 本回合结果
↓
玩家选择：
A. 不修改规则
B. 尝试提交一条新规则
↓
玩家最终点击“继续下一回合”
↓
下一回合开始
```

游戏**不会自动从一回合进入下一回合**。

---

# 5. 规则提交规则

## 5.1 每个回合间都允许尝试制定规则

从第 1 回合结束后的玩家决策阶段开始，每个非终局回合间都允许提交规则。

## 5.2 同一决策阶段最多成功修改一次

规则被拒绝：

- 不增加“规则制定次数”；
- 当前 active rule 不变；
- 玩家可以改写后再次提交。

第一次成功：

- 新规则替换旧规则；
- `rule_change_count += 1`；
- 本决策阶段不再允许第二次成功替换；
- 规则输入区锁定；
- 玩家仍需点击“继续下一回合”。

## 5.3 始终最多一条 active rule

```text
旧规则
↓ 被新规则替换
新规则成为唯一 active rule
```

V0.2 不做规则叠加。

规则持续到：

```text
UNTIL_REPLACED
```

## 5.4 提交成功不自动推进回合

成功后先显示：

- 规则已生效；
- 系统最终接受的结构化规则；
- 红蓝双方有效属性变化。

玩家确认看完后再点击：

```text
继续下一回合
```

---

# 6. 规则制定次数

玩家界面必须持续显示：

```text
规则制定次数：N
```

定义：

- 只统计**成功生效**的规则替换；
- 被拒绝的尝试不计数；
- 同一个幂等请求重试不重复计数；
- 规则制定次数 V0.2 暂不直接参与得分。

后台可以另记：提交尝试数、拒绝数、模型不可用数等，但不作为主界面核心数字。

---

# 7. 当前玩家目标与成绩

V0.2 第一版目标：

> **让战斗持续尽可能多的完整回合。**

玩家主成绩：

```text
score_rounds = completed_rounds
```

AI 对局结果与玩家成绩分开显示。

例如：

```text
红方胜利

本局持续：14 回合
规则制定：4 次
```

当前 `max_rounds = 30`。

如果双方达到 30 回合上限，对 AI 来说可以仍是 `TIMEOUT`，但对玩家 UI 应表达为：

```text
达到本局最高回合数
本局成绩：30
```

而不是“玩家失败”。

未来可以增加不同关卡目标，但不在本次 MVP 内提前实现。

---

# 8. 不加入回血

V0.2 明确：

- 没有基础回血；
- 当前 Rule DSL 不支持回血规则；
- 玩家不能通过自然语言创建回血；
- HP 一旦因伤害下降，不会自然恢复。

原因：有限 HP 是当前延长对局玩法的重要资源约束。稳定回血极易让最优策略退化成无限恢复循环。

未来若实验需要恢复机制，只能作为独立设计议题重新评估，不得直接扩 DSL。

---

# 9. “战局升温”——把防死局机制产品化

当前 Engine 的 `no_damage_streak / conflict_level / hard_liveness` 不再只当内部工程兜底，产品层统一称为：

> **战局升温**

目的：玩家既不能让双方过快互杀，也不能无限让双方完全不造成伤害。

当前阈值保持现有实现，暂不凭感觉改数值：

| 连续无实际伤害回合 | 战局升温 | 当前系统效果 |
|---:|---|---|
| 0–2 | 0级 | 无额外破局加成 |
| 3–5 | 1级 | 提高攻击距离下限 |
| 6–8 | 2级 | 弓射程继续提高，最低命中率 25% |
| 9–11 | 3级 | 弓射程继续提高，最低命中率 50% |
| ≥12 | 4级 | 强制破局：全图弓射程、100%最低命中，并可强制弓攻击 |

此外现有 Round 24 hard-liveness 兜底继续保留，直到新的节奏实验提供证据再修改。

## 9.1 规则修改不能重置战局升温

```text
修改规则 ≠ 造成伤害
```

因此替换规则时：

- `no_damage_streak` 不归零；
- 战局升温等级不因换规则重置。

只有本回合产生**实际应用伤害**时，连续无伤害计数才归零。

## 9.2 UI 必须可解释

不要向普通玩家显示 `Hard Liveness`、`conflict_level` 等英文工程名。

建议 UI：

```text
战局升温：0级
连续无伤害：2回合
再持续1回合无伤害，双方攻击范围将提高
```

达到更高等级时明确告诉玩家发生了什么。

# 10. AI 信息展示

V0.2 不展示完整模型内部思维过程、chain-of-thought 或 private memory。

玩家看到的是**公开策略摘要**。

当前内部四枚举在 UI 中使用中文：

| 内部值 | 中文 UI |
|---|---|
| `PRESSURE` | 逼近进攻 |
| `KITE` | 保持距离 |
| `EVADE` | 躲避保命 |
| `HOLD` | 原地应对 |
| `RED` | 红方 |
| `BLUE` | 蓝方 |
| `BOW` | 弓箭 |
| `KNIFE` | 刀 |

当前可展示：

```text
当前策略
本回合目标
武器倾向
风险倾向
```

后续 richer-plan 若通过 A/B/C 验证，可增加目标距离、短期目标、应变方案等。

公开策略摘要与实际动作必须分开显示：

```text
AI 想做什么
≠
Planner 最终生成什么动作
≠
Engine 最终发生什么结果
```

# 11. 游玩界面信息层级

主界面保持三栏：红方 / 棋盘 / 蓝方。

推荐结构：

```text
┌──────────────────────────────────────────┐
│ 第 N 回合 / 已完成 N 回合   规则制定次数 │
│ 当前公共规则                             │
│ 战局升温                                 │
├────────────┬──────────────┬─────────────┤
│ 红方       │              │ 蓝方        │
│ 生命值     │              │ 生命值      │
│ 当前策略   │    5×5棋盘   │ 当前策略    │
│ 实际行动   │              │ 实际行动    │
│ 当前属性   │              │ 当前属性    │
├────────────┴──────────────┴─────────────┤
│ 本回合结果 / 事件摘要                    │
├──────────────────────────────────────────┤
│ 公共规则输入框                           │
│ [提交规则]                [继续下一回合] │
└──────────────────────────────────────────┘
```

原则：

- 玩家可见文案尽量中文；
- 不把内部 enum / provider / schema 名直接丢给普通玩家；
- 中间棋盘是战局视觉中心；
- 左右红蓝信息对称；
- 公共规则只在中央展示一次；
- 红蓝各自显示规则最终造成的有效属性变化。

# 12. Replay

终局后提供：

```text
重新开始
查看本局回放
```

Replay 至少能解释：

- 第 1 回合无玩家规则的基线战斗；
- 每个回合双方公开策略；
- 具体动作和 Engine 事件；
- 玩家在哪个回合后尝试提交规则；
- 规则被接受或拒绝；
- 哪条新规则替换了旧规则；
- 规则制定次数如何变化；
- 战局升温如何变化；
- 最终 AI 对局结果和玩家持续回合成绩。

Replay 继续禁止重新调用模型，也不记录完整模型内部推理。

---

# 13. 当前最重要的待验证玩法风险

V0.2 不假装以下问题已经解决：

1. 玩家是否几乎每回合都必定改规则，导致“继续”成为伪选择；
2. 是否存在一套固定规则套路能稳定拖到 30 回合；
3. 当前 3/6/9/12 的战局升温阈值在“每回合人工暂停”的新节奏下是否太慢；
4. 追逃、双 KITE、双 EVADE 是否产生无聊的软死局；
5. 当前四分类 LLM 是否真的比 deterministic heuristic 带来可感知策略差异；
6. 玩家是否能理解公共规则为何对双方产生不同实际效果。

这些必须靠实验和真人试玩回答。

# 14. 对工程实现的立即影响

旧流程：

```text
Round 1 前 Phase 0
每3回合规则阶段
```

已被本规范取代。

因此在继续实现 `MatchApplicationService` 前，必须先完成：

```text
1. 公共 API Contract 升级到 mvp-v0.2
2. MatchSnapshot 增加 completed_rounds / rule_change_count
3. 用玩家决策阶段替代 RulePhaseSnapshot
4. 暴露战局升温公共状态
5. Replay 改为 round + intermission/rule-attempt 时间线
6. DynamicRuleController 迁移到：无 Phase 0、每个非终局回合后进入玩家决策阶段
7. contract / controller tests 更新
```

在上述迁移完成前，不应该继续把旧 cadence 写进新的 MatchApplicationService。
